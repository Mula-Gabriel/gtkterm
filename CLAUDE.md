# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

GTKTerm is a GTK+3 serial-port terminal emulator for Linux (this is a fork with substantial macro, TCP-transport, and Lua-scripting additions). Written in C, built with Meson/Ninja. Comments and commit messages are in French.

## Build / Run

```sh
meson setup build        # once (build/ already exists here; re-run only after meson.build changes)
ninja -C build           # build — the common edit/compile loop
./build/src/gtkterm      # run
meson test -C build      # tests unitaires (GLib GTest) + syntaxe des exemples Lua
meson test -C build --suite gui   # suite graphique (broadway + AT-SPI isolés, jamais l'écran réel)
sudo meson install -C build --no-rebuild   # system-wide install after `ninja -C build` (+ gtk-update-icon-cache)
```

A PostToolUse hook (`.claude/settings.json`) runs `ninja -C build` automatically after edits to `src/*.c|*.h`, so compile errors surface immediately.

**Tests:** `meson test -C build` runs GLib GTest unit tests (`tests/`) against `gtkterm_core`, a static library of the GTK-free modules (`transport.c`, `history.c`, `rx_transform.c`, `device_match.c`, `view_render.c`, `serial_termios.c`, `config_file.c`, `profile.c`, `config_store.c`, `rx_queue.c`, `script_port.c`, `macros_format.c`, `macros_list.c`, `macro_set.c`, `macro_file.c`, `macro_poller.c`, `baudrates.c`, `baud.c`, `i18n.c` — see `core_sources` in `src/meson.build`) linked by both the app and the tests, plus integration tests that compile real `src/` modules (`link.c`, `macros.c`, `script_engine.c`) against UI stubs (`tests/stubs/`); plus `luac -p` on `scripts/*.lua`. Meson builds test executables with plain `ninja` too; configure with `-Dtests=false` (`meson_options.txt`) to skip the suite — the self-update script does. Cases tied to a known bug from `docs/superpowers/reviews/2026-10-06-revue-code.md` are marked with its ID and reported as `# TODO` without failing the suite (list them with `grep '# TODO' build/meson-logs/testlog.txt`; `meson test -v` only shows `EXPECTEDFAIL`); a marked case that starts passing fails, so the marker gets removed with the fix. See `tests/README.md` (sanitizers, valgrind, how to add a test). There is no remote CI: tests run locally. GUI behavior is covered by the `gui` suite (`tests/gui/`, see `tests/README.md`).

Dependencies: `gtk+-3.0`, `vte-2.91`, `gudev-1.0`, `lua5.4`, `gtksourceview-4`. `jq` is **not** installed — shell scripting here uses `python3` for JSON.

## Architecture — the data flow that spans files

**Layers (sub-project 2):** the GLib-only core (`gtkterm_core`: `transport.c`, `history.c`, `rx_transform.c`, `device_match.c`, `view_render.c`, `serial_termios.c`, `config_file.c`, `profile.c`, `config_store.c`, `rx_queue.c`, `script_port.c`, plus the older macro/baud/i18n helpers), the link (`link.c`, `GtkTermLink` GObject + GUdev) and the GTK 3 UI. The UI never talks to the transport directly.

**Receive path (device → screen):** `transport.c` reads bytes → `on_data` callback → **`link.c`** appends them to the `GtHistory` (RX record with its wall time) and emits `received (GBytes *data, gint64 wall_time_us)` → subscribers: `terminal_display.c` (renders through `view_render.c`, then `vte_terminal_feed()`), `logging.c` (own `GtRxTransform`, no echo), `files.c` (wait-for-char during file send), the Lua engine (port 0, connected on the main thread).

**Send path:** everything goes through `gt_link_send(link, data, len, GtSendOrigin)` (keyboard, macro, Lua, hex, file). Only bytes actually written are appended to the history (TX record) and emitted by `sent`; echo is rendered from that, so it stays in place across view switches. The history keeps **raw** bytes: CR/LF auto and timestamps are a read-time transform (`GtRxTransform`), so toggling an option, the echo or the view redraws the terminal from the history (`terminal_display_redraw()`).

**Transport (`transport.c` / `transport.h`):** one instance per opened port (`gt_transport_open(params, callbacks, user_data, GError **)`), three modes — `TRANSPORT_SERIAL`, `TRANSPORT_TCP_CLIENT`, `TRANSPORT_TCP_SERVER`; no UI calls, errors via `GError`, `LOST` reported (deferred to an idle) instead of reconnecting. Serial specifics: termios in `serial_termios.c`, baud-rate tables in `baud.c`/`baudrates.c`. Privileged TCP ports use `CAP_NET_BIND_SERVICE`.

**Link (`link.c` / `link.h`):** single state machine for the main port — `CLOSED`, `CONNECTING`, `OPEN`, `LISTENING`, `LOST`, `RECONNECTING`; properties `state`, `status-text`, `auto-reconnect`, `reconnect-interval-ms`; signals `open-failed` (user-requested open only → error dialog), `received`, `sent`, `history-cleared`. Link loss never opens a dialog: the status bar shows « — lost » / « — reconnecting… »; silent retry every 2 s plus an immediate retry when udev reports the device back. With `auto-reconnect`, a failed user-requested open (serial or TCP client) shows `open-failed` once, then goes to `RECONNECTING` too (device plugged in / server started after GTKTerm). The udev monitor lives here and matches by device number, then path/links (`device_match.c`). **Re-entrancy (see `link.h`):** handlers of `received`, `sent` and `notify::state`/`notify::status-text` may run inside the transport's fd watch or inside `gt_link_send`; they must not call `gt_link_open`/`gt_link_close` nor run a nested main loop (`show_message`, `gtk_dialog_run`) — defer with `g_idle_add`.

**Lua scripting (`script_engine.c` + `script_panel.c`, sub-project 5):** scripts run on a **background GThread** (`g_thread_new("lua-script", …)`). The Lua thread never touches GTK, a transport or the link: it only uses the receive queues (`GtRxQueue`, `rx_queue.c`: locked, 1 MiB, oldest bytes dropped, overflow reported once per port and run) and the atomic port state, and runs everything else on the main thread through `run_on_main_sync` (direct call when invoked from the main thread, recorded by `script_engine_setup`). Lua ports 1–15 are `GtScriptPort` (`script_port.c`, core: one `GtTransport` + one `GtRxQueue` each, opened/closed/written on the main thread; the port table is read and written by the Lua thread only); port 0 is the link, observed through its `received` signal (connected/disconnected on the main thread); its queue is never closed, so `wait_for(0, …)` returns only data or `"timeout"`. `send`/`send_hex` write everything or fail with a reason (partial writes and `EAGAIN` retried on the Lua thread with a 2 ms pause, timeout); failures return `false`/`nil` plus a stable English reason; a `tcp_client` connection with a timeout of 0 or a negative one returns `"timeout"` at once; its host name is resolved on the Lua thread (`getaddrinfo`, not interruptible) and each address is then opened by its numeric form and tried in turn within the timeout (the transport itself also falls back to the next address on an asynchronous refusal). Closing a serial Lua port (`close` or end of script) first waits on the Lua thread for pending output (`TIOCOUTQ` polled every 5 ms via `run_on_main_sync`, at most bytes × 10 / baud + 500 ms, then a pause for the UART FIFO / USB buffers (64 bytes × 10 / baud + 10 ms, even when nothing is pending), all under a single 2 s deadline), never when a stop is requested, because the transport's close discards it (`TCOFLUSH`). The Lua thread switches only `LC_NUMERIC` to `C` (numbers keep their point), so its messages (`Lua error: …`, buffer overflow) are translated like the rest. A `tcp_client` failure reason names the host given by the script before the numeric address tried last (`Cannot connect to localhost (127.0.0.1:4000): …`). Before `lua_close`, the stop flag is set so `__gc` finalizers cannot open ports or wait. « Stop » sets an atomic flag: every `gtkterm.*` function and `print` is wrapped by `api_guard`, which raises the stop sentinel as soon as it is requested (a stop writes no « Lua error » line); a count hook (`lua_sethook`, every 1000 instructions, then every instruction once stopping) raises it for code that calls nothing of the API, so a script's `pcall` cannot keep swallowing it; blocking calls (`sleep` on a `GCond`, `wait_for`, connect wait, send retries) check it at least every 20 ms. Blocking standard-library functions (`os.execute`, `io.read`/`lines` (and its iterator)/`popen`/`open`/`write`, file `read`/`lines`/`write`) are wrapped by `std_guard`, which sees the stop on entry and gives argument errors back their position and function name. Limits: long C calls (`io.read`, `os.execute`, a huge `string.rep`, pathological patterns) are only interrupted when they return; a loop calling only the standard library sees the stop every 1000 instructions; `debug.sethook` is removed but `package.loadlib` can bypass that. `os.exit(n)` ends the script (never GTKTerm): 0 → finished, any other code → error, code not truncated; `print` writes to the console; the script runs inside `lua_pcall` of a C function. Log text is batched in a locked buffer flushed by a single source at `G_PRIORITY_DEFAULT_IDLE` (20 ms timer, 1 MiB cap with a dropped-bytes line); the done idle flushes it, joins the thread, then reports `GtScriptEnd` (finished / error / stopped). **Closing GTKTerm:** destroying the main window (`on_main_window_destroy` in `interface.c`) detaches the link handlers, the status LEDs and the macro polling, then stops the script; `script_engine_shutdown()` (called by `main` after `gtk_main()`) does not run the main loop any more: the main thread itself executes the pending `run_on_main_sync` requests until the thread ends, and abandons the thread after 3 s. `script_panel.c` is the editor/console UI (GtkSourceView 4, console capped at 10 000 lines). **When adding a `gtkterm.*` function: work on the Lua thread, run any GTK/transport/link side effect on the main thread via `run_on_main_sync`, never hold a queue lock across it, register it through the guarded wrappers (`api_guard`), and make any blocking wait check `stop_requested` at least every 20 ms.** Example scripts live in `scripts/` (use the `/lua-script` skill to scaffold new ones).

**Macros subsystem (sub-project 4):**
- `macro_set.c` (core) — `GtMacroSet`: ordered macros with a **stable in-memory id** (never reused), label/shortcut/action/tab, stored arguments, polling mode + period (1 ms – 24 h), its own named lists (`GtMacroLists`, `macros_list.c`); `gt_macro_expand()` is the only expansion (format then escapes; `n_args < 0` = stored arguments); `gt_macro_set_apply_edits()` applies the edit window rows by id, so arguments and polling follow the macro, never the position.
- `macros_format.c` (core) — printf-style arguments (`%d`, `%s`, `%#ListName`, length modifiers); the lists are passed in (`%#x` is a list only if list `x` exists).
- `macro_file.c` (core) — the standalone `.ini`: v2 format (`[gtkterm-macros] version=2`, `[macro:N]`, `[list:N]`, values escaped by GKeyFile); old `[macros]`/`[lists]` files are read and rewritten as v2 on the first save. Before overwriting any present, non-empty file that is not a readable v2 (old format, bad syntax, unknown version, foreign file), the save makes a one-time copy `<file>.avant-migration`; if that copy already exists with a different content, the save is refused and nothing is overwritten. A file with groups but none of `[gtkterm-macros]`/`[macros]`/`[lists]` is refused on load (`G_KEY_FILE_ERROR_GROUP_NOT_FOUND`); an empty file gives an empty set. A non-interactive load failure (profile) still makes that file the current path (empty set, warning + deferred dialog), so later saves never fall back to the default file.
- `macro_poller.c` (core) — polling scheduler: one GLib timeout per running macro, sends through a callback (the app's `macros_send`), state callback to the panel. The running state is never saved.
- `macros.c` (UI) — the app's macro state (current set, file path, poller on the default link), `macros_send(id, args, n)` — the **only** macro send path (panel click, shortcut, polling, Lua) —, shortcuts connected by id, the edit window.
- `macro_panel.c` (UI) — the button panel, a view of the set and the poller (argument fields write to the model; rebuilding never touches polling).

Macros and lists live in that standalone `.ini`, separate from the port config; the last-used path is remembered in the active profile of `.gtktermrc`.

**Config (`config_store.c` + `profile.c` + `term_config.c`):** `.gtktermrc` under `$XDG_CONFIG_HOME` (migrated from `$HOME`) is read and written only by `GtConfigStore` (GKeyFile): `[general]` (update settings), `[profile:NAME]` (one `GtProfile` each), and the owner groups `[window]` (window state, `term_config.c`), `[colors]`, `[layout]`, `[session]` (`script_panel.c`), which access their groups through `gt_config_store_get_key_file()` then `config_save_store()`. Old parsecfg files are migrated in memory on load, with a one-time backup `.gtktermrc.avant-migration`. The running profile is the global `GtProfile config` (command-line options apply to it only); only explicit saves write a whole profile; loading a macros file writes only the active profile's `macros_file` key (and only if the path changed and the profile still exists), closing the About dialog only `update_url` in `[general]`, and only if it changed. Several GTKTerm instances share the file: every UI write calls `config_reload_store()` first (re-read if the file's identity changed — `gt_config_store_reload_if_changed()`), applies its single change, then saves; keep that order when adding a writer. An unreadable file makes the store read-only: nothing is ever written over it.

**Self-update (`update.c` + `data/gtkterm-update.sh`):** the running binary knows its own commit because `src/meson.build` generates `git_revision.h` (`GIT_REVISION`) with `vcs_tag()` on every build (with `safe.directory=*` so a root rebuild keeps the real SHA). Install as root with `meson install --no-rebuild`, never `sudo ninja install`: right after a commit, a root `ninja` rewrites `build/src/git_revision.h` as root and the next user build fails with Permission denied. `update_check()` runs `git ls-remote <update_url> HEAD` asynchronously (`g_subprocess`) and compares the remote SHA against `GIT_REVISION` — silent at startup unless a newer revision exists (skippable), always reporting when triggered manually from the About dialog. Accepting launches `data/gtkterm-update.sh` (installed under `PACKAGE_DATA_DIR`, also baked by meson) inside a detected terminal emulator; the script clones/updates into `$XDG_CACHE_HOME/gtkterm/src`, installs build deps, builds, `pkexec`-installs, and restarts the app by PID. The repo URL and install prefix come from `settings.update_url`/`settings.update_prefix` (`[general]` of `.gtktermrc`; the URL is editable in the About dialog; defaults to the GitHub fork and `/usr/local`).

**Other entry points:** `gtkterm.c` (`main`, wiring order; schedules the startup update check via `g_idle_add`), `interface.c` (the large GTK GUI — menus, VTE widget, view switching, shortcuts, About dialog), `link.c` (port state machine, GUdev hotplug), `user_signals.c` (SIGUSR1/2 → open/close port), `cmdline.c` (CLI options incl. `--transport/--host/--tcp-port`), `search.c`, `logging.c`, `files.c`, `i18n.c` (gettext; translations in `po/`).

## Code style

The codebase is **mixed-style** — be deliberate. The dominant style (`link.c`, `interface.c`, `term_config.c`) is **tabs**, **Allman braces** (`{` on its own line), and **no space before `(`** (`if(cond)`, not `if (cond)`). A few files (e.g. `terminal_display.c`) use a different GNU-ish 2-space style. **Match the style of the file you are editing.** A `.clang-format` encoding the dominant style is present, but do NOT bulk-reformat existing files — it would create huge diffs across the mixed styles. Format only new code / new files intentionally.
